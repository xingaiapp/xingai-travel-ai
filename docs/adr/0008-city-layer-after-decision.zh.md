# ADR 0008：目的地决策之后的城市层

**状态：** Accepted  
**日期：** 2026-09-30  
**作者：** Xing @ XingAI  
**取代：** —  
**被取代：** —  
**语言：** [English](0008-city-layer-after-decision.md) · 中文

## 背景

Travel AI 回答的是"我该去哪？"（[ADR 0001](./0001-compare-first-product-scope.zh.md)）。旅行者选定城市之后，第一次去的人问的是另一个问题："有哪些地方值得知道？这几天怎么玩？"目前产品停在 `/result` 页生成的行程上：看不到地点在地图上的位置，没法比较几种玩法，也查不到某个说法的出处。

我们要补上这一层，以香港作为第一个参考城市。这是产品范围的变化，不是一个功能开关：

- ADR 0001 把"多城市路线引擎"列为不做。城市层属于目的地内的路线规划，ADR 0001 当时没有考虑到。
- 现有三个 API（`/api/compare`、`/api/inspire`、`/api/plan`）都在请求里现场调用 OpenAI。工作区对 XingAI 后端的规则是：请求只读预先算好的数据，不现场调用外部服务。再加一个"用 AI 定制"接口，只会把这个缺口扩大。
- 由发布者编写的城市指南，同样会遇到 [ADR 0004](./0004-affiliate-after-decision.zh.md)（佣金）和 [ADR 0006](./0006-stories-after-decision.zh.md)（作者偏好）解决过的偏差问题。
- 开放时间、价格、闭馆和活动信息都会过期，而这个仓库没有负责刷新它们的 worker。

## 决策

**城市层是目的地决策之后的可选阅读。它由人工审核过的静态数据生成，不在请求时调用 AI，也不会反过来影响目的地比较。**

### 1. 位置

1. 路由为 `/city/[slug]`，由城市注册表静态生成。上线时只有香港（`/city/hong-kong`）。
2. 入口：
   - `/result` 页，在决策完成之后、"相关故事"旁边。**任何**参与比较、并且有城市页的目的地都会显示，顺序按比较顺序，匹配规则与 `storiesForDestinations()` 相同。
   - 香港故事季的页面。
   - 通过 sitemap 和 `llms.txt`，从搜索直接进入。
3. 底部导航和侧边导航保持不变（`/decide`、`/stories`、`/trips`），城市层不新增 tab。
4. 城市数据不传给 `/api/compare`、`/api/inspire` 或 `/api/plan`，prompt 里也不能提到。一个目的地有没有城市页，都不能改变胜出者、排名、信心或权衡说明。

### 2. 数据与证据

1. 城市数据放在 `lib/cities/`，是带类型、经过人工审核的 TypeScript，包含地点、地理片区和路线。运行时没有数据库，没有 API 路由，也没有 LLM。
2. **第一版只写稳定事实：** 坐标、所在区域、地点类型和历史意义。每个地点至少记录一条来源（`sourceName`、`sourceUrl`、`retrievedAt`）。
3. **第一版不写动态信息：** 开放时间、票价、闭馆、交通状况、活动、天气、预约和当前热度。页面上直接说明这些不在覆盖范围内，出发前要自己确认。这比挂一个标着"未核实"的过期数值要好。
4. 站点之间的交通时间标为"估算"，不当作时刻表展示。
5. "星哥推荐"可以作为地点卡上的标签出现，并注明是一个人的亲身选择。它不能写进任何路线的"为什么选这条"。这一条沿用 ADR 0006。

### 3. 路线

1. 香港有三条人工编写的参考路线：经典（Essentials）、拍照（Photo）、在地（Local）。这些路线不由 LLM 生成。
2. 每条路线都有**为什么选这条**、**适合谁**和**代价**三部分。任何一条都不标"最佳"。
3. 构建时做检查。出现以下情况时构建失败：
   - 路线引用了不存在的地点；
   - 离开某个片区后又绕回去（走回头路）；
   - 某个站点没有写理由。

### 4. 调整开关（代替 AI 定制）

1. 第一版提供确定性的开关，例如"下雨"、"少走路"、"时间短"、"多吃点"。每个开关都是作用在结构化路线和地点数据上的纯函数：删除、替换或重排站点，只使用数据集里已有的地点。
2. 每处改动都写明原因，例如"把太平山换成 M+，因为太平山在户外、受天气影响"。如果某个开关排不出合理的路线，就直接说明，不硬凑一条质量差的路线。
3. 基于 LLM 的定制不在本次范围内。以后要做的话，需要单独写 ADR，并遵守只读的请求路径：由 worker 提前生成并验证结果，请求只负责读取。

### 5. 地图

1. 第一版用内嵌 SVG 画香港岛和九龙各片区的示意图，不需要地图图块，也不需要 API key。站点和路线时间线双向联动高亮。
2. 每个站点都有一个"在地图中打开"的链接，由坐标生成。逐路导航交给旅行者手机上的地图 App。
3. 交互式图块地图推迟，另写 ADR，内容包括图块服务商、使用政策和手机端性能。

### 6. 照片、语言与联盟链接

1. 照片优先用亲手拍摄、经过 `scripts/process-story-photos.mjs` 处理的图片，这个脚本会去掉 EXIF 和 GPS 信息。没有的话，用有授权的图片，并在数据里记录署名。都没有的话，就不放照片。图片里不能有文字。
2. 城市文案必须提供全部四种语言（`en`、`zh`、`ko`、`es`）。和故事不同，城市文案不能回退到英文，由类型系统强制检查。
3. 第一版城市页不放联盟链接。`/result` 页继续遵守 ADR 0004。

### 7. 衡量

`POST /api/track` 新增两个事件类型：`city_from_result` 和 `city_route_select`。30 天后做一次检查，决定是继续做第二个城市、调整这一层，还是停掉。

### 明确禁止

- 在参考路线之间打"最佳路线"标签，或用任何"只有一个赢家"的方式呈现。
- 展示没有实时、带日期来源的开放时间、价格或活动日期。
- 城市层在请求时调用 LLM 或第三方 API。
- 单独做一个香港小应用、第二套设计系统，或新增顶级导航。
- 把"有没有城市页"或城市页内容用在目的地比较里。

## 后果

**正面**

- 第一次去的人大约一分钟内就能看到值得知道的地点、片区划分，以及三种玩法各自的理由和代价。
- 页面上每个说法都有出处，不会有内容悄悄过期。
- 这一层不增加 API 成本和延迟，也不需要新的密钥。
- 组件接收 `City` 数据，所以加第二个城市只需要加数据，不需要重写。

**负面**

- 没有开放时间和价格，旅行者仍要去别的网站查这些信息。
- 示意地图不如图块地图精确，所以每个站点都外链到真正的地图 App。
- 确定性开关能覆盖的需求比自由输入的 AI 定制少。
- 每个城市的数据都要人工编写，覆盖面会增长得比较慢。

## 曾考虑的替代方案

- **每次请求由 LLM 生成行程：** 否决。会编造内容，无法验证，还会在请求里增加一次外部调用。
- **展示动态信息，但标"未核实"：** 第一版否决。没有刷新用的 worker，过期的数据会比核实过的多。
- **现在就上交互式图块地图（Leaflet / MapLibre）：** 推迟。在证明这一层有用之前，图块政策、API key 和包体积的成本不值得。
- **把城市层放进 `/result`：** 否决。结果页会长很多，城市内容也会被绑在某一次会话的结果上。
- **先做通用的多城市框架：** 否决。应该在做第二个城市时再抽象，而不是提前。
